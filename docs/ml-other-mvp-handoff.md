# Передача сценария ML-рекомендаций «Другое»

## Пользовательский сценарий

1. Статические категории отправляются обычным способом и не требуют ML.
2. Для категории `other` нажатие «Отправить» сначала вызывает backend-рекомендацию.
3. Backend сам выбирает не более 16 активных кандидатов того же дома и допустимого временного
   окна. Фронтенд не передаёт список кандидатов в ML.
4. ML возвращает ранжированный список. Фронтенд показывает до трёх карточек со score не ниже
   `0.88` и всегда показывает «Создать новый инцидент».
5. Финальный выбор передаётся в Incident Core как `CONFIRM_INCIDENT` или `FORCE_NEW`.
6. Core повторно проверяет дом, категорию и активность выбранного инцидента под блокировкой.
   ML не пишет в БД и не меняет состояния.

При недоступности ML пользователь сразу получает вариант создания нового инцидента. Обращение
не теряется, а семантический сервис остаётся отсоединяемым.

## Детерминированная политика Incident Core

- нет активных кандидатов — `CREATE`;
- один активный кандидат для статической категории — `ATTACH`;
- несколько кандидатов для статической категории — `NEEDS_CLARIFICATION`;
- категория `other` — автоматическое присоединение запрещено;
- подтверждённый пользователем допустимый кандидат — `ATTACH`;
- выбор «создать новый» — `CREATE`.

Свободный текст, regex и n-gram в этих правилах не используются.

## Контракт frontend → backend

Предварительный запрос не должен вызывать публичный ML endpoint напрямую:

```json
{
  "house_id": "uuid",
  "category_code": "other",
  "text": "Сообщение жителя"
}
```

Ответ backend:

```json
{
  "request_id": "uuid",
  "candidates": [
    {
      "incident_id": "uuid",
      "title": "Безопасное агрегированное название",
      "score": 0.91,
      "reports_count": 7,
      "started_at": "2026-09-26T09:00:00Z"
    }
  ],
  "model_version": "maxsmartcity/multilingual-e5-small-int8",
  "scorer_version": "multilingual-e5-query-passage-cosine-v2"
}
```

Сырые сообщения и сведения других жителей в карточку кандидата не входят.

Финальная отправка содержит один из вариантов:

```json
{"mode": "CONFIRM_INCIDENT", "confirmed_incident_id": "uuid", "request_id": "uuid"}
```

```json
{"mode": "FORCE_NEW", "request_id": "uuid"}
```

## Что хранить в итоговой БД

Для MVP новые embedding-таблицы и `pgvector` не требуются. Сначала SQL ограничивает кандидатов
по дому, категории, активности и времени; E5 ранжирует небольшой список в памяти.

Используются существующие таблицы:

- `reports.report` — итоговое обращение;
- `incidents.incident` — инцидент;
- `incidents.incident_report_link` — подтверждённая связь;
- `incidents.incident_grouping_decision` — аудит решения.

В `incident_grouping_decision` для полного аудита желательно добавить nullable JSONB
`candidate_scores` вида `[{"incident_id": "...", "score": 0.91}]`. Остальные необходимые
поля уже есть: выбранный инцидент, top score, runner-up, candidate ids, reason codes,
`policy_version`, `scorer_version` и `request_id`.

Синтетические `reports.jsonl` и `incidents.jsonl` в рабочую БД не импортируются: это только
версионированный benchmark и нагрузочные fixtures.

## Измеренное качество

Test split: 32 запроса, включая 8 случаев `CREATE_NEW`.

- Recall@1: `95.83%`;
- Recall@3: `100%`;
- MRR: `97.22%`;
- порог `0.88`: precision первой рекомендации `86.96%`, recall `83.33%`;
- порог `0.90`: precision `93.33%`, recall `58.33%`;
- порог `0.92`: precision `100%`, recall `45.83%`.

Для MVP рекомендуется показывать до трёх кандидатов от `0.88`, всегда оставлять «Создать
новый» и не выполнять auto-attach. Реальные пользовательские подтверждения следует сохранять
как будущую human-reviewed выборку.

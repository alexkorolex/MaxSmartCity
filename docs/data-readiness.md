# Данные для проверки, ML и карты

## Что действительно требуют организаторы

Для решения с собственным API нужны воспроизводимые тестовые данные в JSON/CSV или другом
согласованном формате. Организаторы не требуют публиковать обучающую выборку или раскрывать
исходные ответы внешнего LLM API. Проверяющему нужны данные и учётные записи, позволяющие
пройти основной сценарий на зафиксированном commit.

Минимальный сдаваемый набор:

- один тестовый житель с выбранным домом;
- сотрудники необходимых ролей;
- 2–3 дома, категории и организации;
- активный инцидент для проверки рекомендации «Другое»;
- обращение без подходящего инцидента для проверки создания нового;
- ожидаемые идентификаторы, статусы и HTTP-коды в runbook;
- OpenAPI и `DATA-API.yaml` для проверяемого публичного API.

Пароли, токены и ключи не входят в Git и передаются организаторам защищённым способом.

## Данные ML

| Набор | Назначение | Ограничение |
|---|---|---|
| `ml/data/gold/v2` | Обучение и smoke-оценка классификатора категорий | 522 LLM-assisted текста; нет независимого real/OOD test |
| `ml/data/matching/other-v1` | Benchmark рекомендаций для «Другого» | Синтетические инциденты и обращения на 20 реальных адресах |
| `ml/data/synthetic` | Регрессия и нагрузочные сценарии | Не импортируется как пользовательская информация |

Дополнительная генерация сейчас не нужна для демонстрации MVP. Она не устранит главный пробел:
нужна небольшая независимо размеченная выборка реальных обезличенных формулировок. До её появления
называйте метрики synthetic/offline benchmark, а ML оставляйте рекомендательным.

## Контракт геолокации

Ingestion уже принимает для дома пару `latitude`/`longitude`, сохраняет точку в PostGIS, а Backend
отдаёт её фронтенду как GeoJSON через `GET /geo/houses/geojson`. Оба значения должны приходить
вместе и проходить проверку диапазона.

Географическое обогащение должно соблюдать правила:

1. Сначала сопоставлять по `fias_id`, затем по стабильному `external_id`; нормализованный адрес
   допустим только при единственном совпадении.
2. Хранить источник, дату получения, лицензию и способ сопоставления.
3. Не подставлять центр улицы или города как координату дома.
4. Не выдумывать прямоугольник здания. Если доступен только центр, отдавать `Point`; контур
   добавлять лишь из источника footprint/polygon.
5. Публиковать покрытие: число найденных, ненайденных и неоднозначных домов по каждому городу.
6. Для повторного запуска не затирать более надёжные реальные координаты демоданными.

Пока источник геолокации не передан, корректный результат — `geometry: null`. После получения
локального файла координат его нужно сначала проверить на схему, дубли и диапазоны, затем собрать
отдельный обогащённый JSON и отчёт покрытия. Исходную выгрузку оставьте без изменений.

# Схема презентации MaxSmartCity

Структура рассчитана на критерии онлайн-этапа «Умного города». Первый слайд служебный и
не оценивается. Переносите в презентацию только подтверждённые значения; поля в
угловых скобках заполняются перед сдачей.

## Слайд 1. Техническая проверка

- MAX: `<ссылка на работающего бота или Mini App>`.
- Репозиторий: `<URL>`, проверяемый commit: `<полный SHA>`.
- Backend API: `<публичный HTTPS URL>`, Swagger/OpenAPI: `<URL или файл>`.
- Тестовые роли: житель, сотрудник УК/ТСЖ, управа, администратор. В сдаваемой организаторам
  версии указать рабочие доступы и переменные, нужные для проверки; из публичной версии
  слайда удалить секреты.
- Запуск: `docker compose --env-file .env up --build` либо фактическая команда сдаваемой
  версии.
- Основной сценарий: житель входит через MAX → выбирает дом и категорию → создаёт обращение
  → при необходимости подтверждает похожий инцидент → сотрудник берёт проблему в работу
  → публикует решение → житель подтверждает результат или открывает спор.

## Слайд 2. MaxSmartCity и команда

- Одно предложение: сервис в MAX, который объединяет обращения жителей в городские
  инциденты и делает ход решения прозрачным.
- Участники и зоны ответственности: product/frontend, Backend/Incident Core, ingestion,
  ML/data, инфраструктура.
- Один скрин главного экрана, без архитектурных деталей.

## Слайд 3. Пользователь и проблема

- Приоритетный сегмент: житель многоквартирного дома; второй пользователь — сотрудник
  управляющей организации или городской службы.
- Сейчас одинаковые сообщения приходят разрозненно, статус и ответственный непрозрачны,
  а повторные обращения создают дополнительную ручную работу.
- Отделить факты от гипотез: привести наблюдения команды, результаты интервью или явно
  подписанное допущение. Не выдавать синтетический датасет за пользовательское исследование.

## Слайд 4. CJM: как было и где возникает потеря ценности

Таблица из пяти шагов: заметил проблему → нашёл канал → описал → ждёт → проверяет результат.
Для каждого шага показать действие, боль, эмоцию и возможность продукта. Основные разрывы:
непонятно, куда писать; неизвестно, есть ли уже такая проблема; нет единого статуса; решение
может быть закрыто без подтверждения жителя.

## Слайд 5. Новый пользовательский путь

Показать один линейный сценарий на 5–6 экранов:

1. вход через MAX;
2. выбор дома и типовой категории;
3. текст и вложение;
4. для «Другого» — похожие активные инциденты и обязательный выбор «Создать новый»;
5. отслеживание статуса и чат;
6. подтверждение решения или спор.

Подчеркнуть: ML предлагает, пользователь решает; сбой ML не блокирует отправку.

## Слайд 6. Ценность для жителя и исполнителя

- Житель получает единый статус, ответственного, историю и возможность оспорить закрытие.
- Исполнитель видит не поток дублей, а один Incident с числом обращений, домами, историей,
  назначениями и обратной связью.
- Администрация получает агрегируемые данные по территориям и категориям.
- Ожидаемый эффект оформить как гипотезы пилота, а не как уже достигнутый результат.

## Слайд 7. Как Report превращается в Incident

- `Report` — сообщение конкретного жителя; `Incident` — общая устраняемая проблема.
- Для типовых категорий Incident Core применяет детерминированные правила по дому,
  категории, активности и временному окну.
- Для «Другого» Backend передаёт небольшой допустимый набор кандидатов локальной
  embedding-модели; пользователь подтверждает связь или создаёт новый Incident.
- Машины состояний и ограничения БД не дают перескочить обязательные этапы или создать
  две активные связи одного обращения.

## Слайд 8. Архитектура решения

Схема: MAX/Mini App/Admin → Backend → PostgreSQL/PostGIS, Redis, MinIO; отдельно ML по HTTP,
Keycloak, MAX API и observability. Указать роли каталогов `src/domains`, `src/ml` и `ml`.
Показать отказоустойчивый путь: недоступность ML → пустая рекомендация → создание нового
инцидента остаётся доступным.

## Слайд 9. Данные и интеграции

- Публичная выгрузка ГИС ЖКХ: 33 822 уникальных дома в Брянске и Бахчисарае после
  дедупликации, с внешними/FIAS ID и provenance.
- Координаты в исходной выгрузке отсутствуют; географию добавлять только из проверяемого
  источника с покрытием и происхождением. Не показывать синтетические контуры как реальные.
- MAX, Keycloak, S3/MinIO, PostgreSQL/PostGIS и локальный ML-сервис.
- Синтетические и LLM-assisted обращения используются только для разработки и benchmark,
  а не как доказательство production-качества.

## Слайд 10. ML: полезная, но отсоединяемая рекомендация

- Модель: локальная квантованная `multilingual-e5-small`, 384-мерные embeddings.
- Задача: ранжировать до 16 уже отфильтрованных активных инцидентов для категории «Другое».
- На синтетическом test split: Recall@1 95,83%, Recall@3 100%, MRR 97,22%; эти цифры
  обязательно подписать как synthetic benchmark.
- Ограничение: независимого human-reviewed real/OOD test пока нет. Следующий шаг — сохранять
  подтверждения пользователей и заморозить обезличенную контрольную выборку.

## Слайд 11. Надёжность, безопасность и проверяемость

- Идемпотентный ingestion, provenance и журнал ошибок; state machines, транзакции и outbox.
- JWT/Keycloak, роли и guards; секреты только через окружение; версии зависимостей закреплены.
- Health/readiness, метрики, трассировки и централизованные логи.
- Привести результаты именно финального commit: тесты, линтеры, Docker build/runtime smoke,
  время сборки и один повторный проход основного сценария.

## Слайд 12. Пилот и измеримый эффект

- Первый пилот: конкретная УК/ТСЖ и ограниченное число домов одного города.
- Метрики: доля обращений с понятным статусом; доля дублей, объединённых после подтверждения;
  медианное время до назначения и решения; доля повторно открытых решений; CSAT жителя.
- До пилота зафиксировать baseline и целевые значения. Не подменять бизнес-метрики F1 модели.

## Слайд 13. Масштабирование

- Сохраняются: модель Report/Incident, контракты, state machines, роли, observability.
- Адаптируются: справочник домов и организаций, территориальная структура, категории,
  маршрутизация, каналы уведомлений и правила конкретного региона.
- Порядок: одна организация → город → несколько городов → регион; на каждом этапе — качество
  данных, ответственный владелец, SLA, обучение сотрудников и обратная связь жителей.

## Слайд 14. Ограничения, риски и следующий шаг

- Нет подтверждённого human test для ML; рекомендации не выполняют автоматических действий.
- Полная карта зависит от легального и воспроизводимого источника координат/контуров.
- Публичный HTTPS, рабочие доступы и чистый запуск должны быть проверены непосредственно перед
  сдачей.
- Ближайший шаг: зафиксировать release commit, пройти end-to-end сценарий в MAX, приложить
  OpenAPI, `DATA-API.yaml`, тестовые данные и runbook.

## Финальная проверка материалов

- Рабочие секреты есть только в закрытой версии для проверки; в репозитории и публичной
  версии презентации их нет.
- Любая метрика помечена как реальная, синтетическая или целевая.
- Диаграммы читаются с экрана; один слайд отвечает на один вопрос.
- Источники указаны рядом с утверждениями либо на отдельном финальном слайде.
